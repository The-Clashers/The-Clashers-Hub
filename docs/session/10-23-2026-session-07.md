## Decisions

- The deployed functions never even loaded: the platform's per-file compile (its bundling mode is env-gated off) kept our extensionless relative imports (`../server/routes`) in ESM output, and Node ESM cannot resolve extensionless specifiers, so every invocation died at module load with ERR_MODULE_NOT_FOUND, surfacing as FUNCTION_INVOCATION_FAILED no matter the export shape. Two changes fix the format: the root package.json drops `"type": "module"` (the .func runtime package.json is copied from it; a module type there would force ESM parsing of the CJS files), and api/tsconfig.json pins `module: CommonJS` + `moduleResolution: node10` for the api and server files the platform compiles, so the output is require()-based and extensionless paths resolve. Verified by loading and driving the actual built artifacts (scripts/launcher-sim.mjs replays the launcher's import, .default unwrap, and Node-style call): search and the dynamic clan function both answer through the mock upstream, with the tag arriving both as the platform's ?tag= query param and as a path segment.
- The platform's Node launcher invokes the default export Node-style, as (req, res). The api adapters export a plain function produced by nodeHandler (server/vercel-adapter.ts), which builds a real Request from the Node req, runs the shared web-standard handler, and pipes the Response into the Node res. If a future launcher calls it web-style instead, the wrapper detects the Request and passes it through; the dev server uses that web-style path.
- The routing manifest (inspected via a local vercel build) puts vercel.json rewrites between the filesystem handle and the generated dynamic-function routes, so a naive catch-all rewrite swallowed /api/clan/:tag and /api/player/:tag into index.html while /api/search (a literal filesystem route) kept reaching its function. The SPA rewrite is now /((?!api/).*) -> /index.html: client routes serve the shell, api paths never match it, and unknown /api paths still 404.
- Dynamic segments reach the function as a tag query param, not in the path: the generated route rewrites /api/clan/:tag to /api/clan/[tag]?tag=:tag. tagFromPath prefers the query param (decoded, with a safe fallback) and keeps the path segment as the fallback for local dev. A unit test locks both behaviors.
- lineHeight tokens stay as design ratios, but createBaseStyles converts each to pixels (ratio x fontSize) via a lineBox helper in one place. RN Web reads a numeric lineHeight as pixels, so lineHeight: 1.2 compiled to line-height: 1.2px under a 36px display font: the line box collapsed and stacked sibling texts on top of each other (the reported "text overlaps" on the deployed home). Screens that already multiplied (TokenScreen, the hello screen description) were correct; only the base styles were not.
- The hardcoded smoke tag is now our own clan #2JPCYP98L: it exists as long as the project does, it is populated (47 members), and its war log is public (verified live: the warlog route answers 200 against it).
- Two local harnesses now guard the platform contract: scripts/platform-sim.mjs replays the Node-style invocation with the manifest's ?tag= dispatch (verify-tier.sh passes 36/36 through it), and scripts/launcher-sim.mjs drives the actually-built artifacts the way the launcher does. Both run against the mock upstream; neither needs a deploy.
