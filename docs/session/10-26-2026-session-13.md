## Decisions

- The normalization rule lives in `src/lib/tag.ts`, not inside the React component. SR-13 says normalization is owned by one component; the rule itself is pure and unit-testable without rendering React, so splitting the rule from the component keeps the test surface small and the rule reusable if a future screen (recent searches, favorites) needs to canonicalize a tag.
- The rule mirrors `server/tags.ts` exactly: leading `#`, uppercase, 3 to 20 characters from `[0-9A-Z]`. The client and the tier never disagree on what counts as a tag; the tier normalizes again cheaply so a stray lowercase still resolves upstream.
- The outcome of normalization is a discriminated union (`{ ok: true; tag } | { ok: false; reason }`), never a thrown exception. Invalid input is a normal state, not an error; the component shows a one-line hint and stays put.
- The reason is a key (`empty`, `too_short`, `too_long`, `bad_chars`), not a sentence. The sentences live in a `REASON_COPY` map inside the component, so wording stays consistent and the unit test asserts the key.
- The hint clears as soon as the user fixes whatever was wrong, not on every keystroke. The component re-runs the rule on each change but only updates state when the verdict changes, so there is no re-render churn while typing valid characters.
- URL encoding happens in `encodeTagForRoute`, the only place the client encodes. The router reads `:tag`, `useParams` decodes it back, so the player screen receives the canonical `#ABC123` form. The `#` becomes `%23` so the router sees one path segment, not a fragment.
- The box sits between the search panel and the results on the entry route, matching the URL map in the feature list (search bar, filter row, tag-lookup box). It is a flat panel, not raised, so the search panel stays the primary surface; the tag box is the secondary path (golden path B).
- The box does no fetch. The player screen owns the fetch and the four state-matrix states that come with it. This keeps the box fast and the navigation concern separate from the data concern.
- `autoCapitalize="characters"` and `autoCorrect={false}` on the input so the on-screen keyboard matches what the rule wants (uppercase alphanumeric), reducing the chance of a `bad_chars` rejection on mobile.
- A character counter (21 - draft.length) sits in the footnote row, quiet and tabular. It gives the user a sense of the 20-char ceiling without a hard stop message.
