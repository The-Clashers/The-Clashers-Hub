## Decisions

- Yes, it needs refactoring, and the doc says so in writing rather than leaving it as chat output. The drift is inventoried in 09 section 10 so it is visible and bounded: one 1018-line screen, two review surfaces with the same threading habit, a named list of magic numbers.
- The threading anti-pattern (whole stylesheets passed as props) is banned outright for new code (STD-13) because the codebase already contains the correct model: TagInput, Dropdown, and ThemeToggle call useTheme and own their styles. The standard generalizes what those three already do.
- The promotion rule (STD-15) is the load-bearing one: anything a second screen needs, anything 07 section 4 names, or anything with its own logic leaves the screen file for src/components/. This is what makes the clan and player screens cheap to build instead of copy-paste exercises.
- Pay-down order: the SearchScreen split is a standalone card before T-M1-3, because building the clan screen on top of the current file would multiply the debt. HelloClanScreen and TokenScreen clean up when next touched, never on their own cards. No big-bang rewrite; behavior stays identical and the golden path plus the tests prove it.
- The standards bind new code immediately; the search screen is the one named exemption until its split lands.
- No source code was touched this session, per the instruction. The refactor itself is proposed as the next card, not smuggled in here.
