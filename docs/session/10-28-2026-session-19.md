## Decisions

- Built on the split kit (session 18), not the old threading pattern. The screen calls `useTheme` and owns one `createStyles`; it renders `StatChip`, `ErrorState`, `EmptyState`, `PillButton`, and `ThemeToggle` from `src/components/`, never receiving a stylesheet as a prop (STD-13). The tab bar stays in the screen file because the 07 section 4 inventory does not name a `TabBar` and no second screen needs one yet (STD-16); it promotes when the war screen or a future surface needs tabs.
- The tab bar reads `?tab=` from the URL so a deep link to the War or Log tab is shareable (F-12). Roster is the default when the param is absent or holds an unknown value, so a stale or typo'd deep link lands on a real tab. Switching uses `setSearchParams(..., { replace: true })` so tab switches are state on the same route, not pages in the back stack: Back leaves the clan, not the previous tab.
- Tab content is a designed placeholder, not a blank panel. Each tab's `EmptyState` names the card that fills it (T-M1-4 for Roster, M3 for War and Log) and what it will render, so the screen reads end to end today and a reviewer knows the gap is by plan, not by oversight. The roster placeholder notes that the clan response already carries the full member list, so T-M1-4 reads from the same single fetch (SR-09).
- The identity header's level and location render as a quiet meta line (uppercase micro) rather than stat chips, because they are identity (what the clan is) not stats (what the clan did). The four stat chips (members, win streak, war wins, points) are the metrics SR-10 names; the kit `StatChip` renders them with the same label-above-value pair the search result cards use.
- Requirements render as a labeled chip row inside the identity panel, not as stat chips, because they are join gates (what the clan asks of applicants), not performance. `requiredTownhallLevel` is omitted from the row when the clan does not set one (the game API omits it for clans with no TH gate), so the row degrades gracefully. `warFrequency` maps through `lib/war-frequency.ts` so the filter dropdown, the search card's War stat, and the identity header's War chip all read from one table.
- The `not_found` error surfaces "Search clans" as its own primary action (navigating to `/`) rather than a retry, because a retired tag cannot be fixed by retrying. The other error branches keep retry as the action; the back-to-search link sits in the footer for every state.
- The client `staleTime` mirrors the tier's 180 s clan TTL (SR-09) so the two cache layers decay together, the same pairing the hello screen and the search screen use (STD-31). The query key is `['clan', tag]`, the full request identity.
- The `memberList` field stays `unknown[]` on the client on purpose. T-M1-4 will add a typed `ClanMember` and parse it in that card's own client or in the roster component; this client only carries the array reference so the roster tab does not need a second fetch. Modeling it now would be guessing at the roster's needs before the roster card is written.
- The build chunk-size warning (520.79 kB) is the same one session 18 noted as M4 perf-pass material; the ~11 kB increase this card adds is the ClanScreen plus the extended client, and it rides the same follow-up, not a new concern.
