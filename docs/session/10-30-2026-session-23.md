## Decisions

- The busy pacing is a capped ladder, not the server's full retryAfter. A
  503 from the tier means the tier already retried the throttle twice
  itself, and its retryAfter defaults to 30 s when upstream sends no
  Retry-After header. Waiting 30 s in a live demo is its own failure, so
  the client polls at 5 s, 10 s, 20 s and takes the server's value only
  when it is shorter. Each client retry costs the tier one bounded
  upstream burst, and three attempts spread over about half a minute keep
  the pressure near zero while giving a throttled key every chance to
  clear. The rule lives in one pure module so the pacing is reviewable
  apart from the screens.
- The pagination footer checks `isFetchingNextPage` before
  `isFetchNextPageError`, and the order is load-bearing: while a retry is
  in flight the query status is still the previous error (status only
  flips on success), so the error flag stays true through the whole fetch
  and would swallow the loading state. Found in the walkthrough, not in
  review: the loading skeleton never appeared on a manual retry until the
  branches were reordered.
- Replacing the footer's "Loading more clans…" text with skeleton cards
  was an accessibility regression until the row carried the progressbar
  role itself: the blocks are decorative and aria-hidden, so nothing was
  left to announce. The row now announces "Loading more clans"; the same
  rule the first-load skeleton wrapper already follows.
- The skeleton shapes compose an atom with a threaded pulse value instead
  of a pulsing wrapper. A wrapper View participates in the layout it
  wraps, and the skeletons are rows (badge beside lines) that a wrapper
  would restack. The atom stays layout-neutral, the pulse costs one loop
  per surface no matter how many blocks it holds, and the block's look
  (hairline fill, chip radius) is owned in one place (STD-22) while the
  screens own only sizes.
- The clan skeleton holds the full page height because that is what
  layout-matched means for a screen whose data lands all at once (SR-09,
  one request): an identity-only skeleton would let the tab bar and roster
  pop in below and reflow the page mid-load. The skeleton's roster follows
  the same 768 px presentation switch the real roster makes, so the shape
  it holds is the shape this viewport will fill.
- The not_found hint explains the tag shape instead of guessing a
  correction. The state matrix words the hint as "maybe you meant", but
  there is no suggestion source for tags (the game API has no search the
  client can mine for near-misses, and inventing one is a tracker's
  problem, not a searcher's). The honest correction is what a well-formed
  tag looks like, the same three rules lib/tag.ts enforces, plus the
  search-by-name action that can actually find the clan.
- The clan screen's loading fragment owns its styles through its own
  createStyles (the RosterSection pattern, STD-13); the success and tab
  fragments keep the threading they shipped with so this diff stays about
  states. Their cleanup rides the next card that touches the screen, the
  same deal HelloClanScreen and TokenScreen have in 09 section 10.
- The mock's search listing pages for real now. A stand-in that returns
  the same clan on every page exercises none of the pagination the real
  client walks (and floods the console with duplicate-key errors, which
  is how the unfaithfulness surfaced). Distinct tags, a cursor walk, and
  a page with no cursor at the end.
