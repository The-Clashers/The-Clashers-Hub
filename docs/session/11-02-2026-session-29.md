## Decisions

- The engine lives in `src/engines/`, not `src/lib/`. STD-09 opens
  `src/engines/` with M2, and the concept doc (05 section 1) says the
  super-troop map is "a plain object in `engines/`." The rushed engine is
  the flagship analysis engine; `lib/` stays home to pure helpers like
  tag normalization and roster sort, `engines/` is for the analysis
  modules with the hard no-React boundary and table-driven tests.
- The engine is split into a CORE and an ADAPTER (05 section 1 "Grouping
  is an adapter's job"). The core consumes generic `UnitLevelEntry` rows
  and never sees the raw payload shape; the adapter re-buckets the
  payload's four arrays into the four categories. That keeps the core
  testable with hand-built entries and decoupled from payload shape
  changes.
- Super-troop normalization drops the super troop entry entirely. The base
  troop entry (which always coexists in the same array, because the game
  requires the base troop to unlock the super) carries the player's real
  lab level. The super-troop map is the identification list: any unit
  whose name is a key in the map is filtered out. The map is data, not
  logic, and a test verifies completeness against the fixture set.
- The super-troop map has 19 entries (the 12 from the scoring doc plus 7
  more super troops the live API returned: Super Miner, Super Minion,
  Super Bowler, Super Hog Rider, Super Yeti, Super Ice Hound, Super
  Inferno Dragon). Completeness is enforced by the fixture-driven test.
- Siege machines and pets are grouped into one category (`petsSiege`),
  matching the scoring doc's "pets/siege" grouping. The game API mixes
  them into the `troops` array without a category tag, so the adapter
  routes them using bundled name Sets. The name Sets are reference data;
  T-M2-6 will formalize them into the reference-data bundle.
- Null-maxLevel entries are skipped and counted in the footnote (SR-14).
  The engine is designed so the reference-data fallback (SR-17) plugs in
  as a maxLevel resolver passed to the core, not a rewrite: when T-M2-6
  lands, the adapter resolves null maxLevel against the reference table
  before handing entries to the core, and the core's skip-with-footnote
  path only fires for units absent from both the API and the reference
  bundle (brand-new content).
- The interpretation bands (05 section 1: 0 maxed, 0-5 core, 5-15 light,
  15-30 rushed, 30+ heavy) are display copy, not judgments of humans.
  The `bandFor` function is pure and tested independently.
- The formula uses equal weights (`w_i = 1`) initially, per the scoring
  doc. Hero weights can be raised later without touching the formula's
  shape: the engine's `totalDeficit` and `totalMax` accumulators are the
  only places weights would enter.
- The top-deficits list is capped at 10. The scoring doc says "top-N";
  10 is enough for the "what to upgrade next" list without overwhelming
  the panel. Deficits are sorted worst-first, tie-broken by name.
- The player client extension adds `PlayerUnit` (name, level, maxLevel
  nullable, village) and four optional arrays on `PlayerResponse`
  (troops, spells, heroes, heroEquipment). The parse is the same
  tolerant shape the identity block already had: a unit without a name
  is dropped; everything else degrades to defaults. The `heroEquipment`
  array is parsed now so the progression grid (T-M2-5) and the rushed
  engine can both read it; the engine counts hero equipment in the
  heroes category.
- Four fixtures under `fixtures/` (SR-07, STD-12): `maxed-player.json`
  (every unit at maxLevel, verifies AC-04 scenario 1),
  `rushed-player.json` (several units below maxLevel, verifies the
  non-zero path), `super-troop-player.json` (every super troop active
  at level 1, verifies AC-04 scenario 2: the normalized level is used
  and the verdict reads maxed), and `null-maxlevel-player.json` (three
  null-maxLevel entries, verifies the skip-with-footnote path).
