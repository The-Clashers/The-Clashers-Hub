## Decisions

- Equipment renders under the hero it is equipped on, from the nested
  `equipment` array the API puts inside each hero entry (observed on the
  live payload: the Barbarian King carries "Spiky Ball" 27/27 and
  "Earthquake Boots" 18/18 there). The payload's flat `heroEquipment`
  array lists every piece the player owns whether equipped or not; that
  inventory reading belongs to the progression grid (FR-16), so the hero
  panel ignores it. This is the "where the API exposes it" reading: the
  per-hero nesting is the only place the payload says which hero an
  item sits on.
- The hero row puts the name and the level/maximum pair on one line
  (heroes carry no requirement text the way achievements do, so the line
  has room), with the LevelRail full width under it, and equipment rows
  indented one spacing step below. The achievements row stacks its pair
  over its rail instead; the difference is data-driven, not taste.
- Equipment rows keep the quiet treatment always (secondary name, muted
  pair, no rails): they are inventory detail under their hero, and the
  pair itself carries the maxed reading ("27 / 27"). Double-muting a
  maxed-equipment row would have no visual room left.
- A maxed hero mutes the same way a completed achievement row does, so
  the heroes still climbing draw the eye and a maxed account reads as a
  quiet ledger. A hero's equipment can still be in progress under a
  maxed hero, so the mute applies to the hero's own line only.
- The null maxLevel never invents a maximum (SR-14's honest-treatment
  rule): the row renders its level alone with no rail, and the card
  footnotes the count ("1 hero is shown without a maximum: the game API
  has not caught up to it yet"). heroProgress returns a discriminated
  union so the render physically cannot reach for a max that is not
  there.
- The count line says "N / M maxed" (formatProgressPair, the same
  formatter the achievements count keeps) with M counting every hero,
  including the ones without a maximum: a hero the API has not caught up
  to counts against the player honestly.
- The village grouping moved to lib/village.ts rather than duplicating
  the rule: two cards need it today (achievements, heroes) and the
  progression grid (T-M2-5) will need it tomorrow, and a shared rule
  with a delegation test cannot drift. The grouping tests moved with the
  rule; the achievements test file keeps only the identity check.
- LevelRail is its own kit component rather than a stars-optional
  ProgressRail: the component inventory is the contract (07 section 4
  names ProgressRail "achievement value/target bar with star markers"),
  and faking a zero-star achievement to reuse the rail would muddy both
  judgments and put the wrong copy ("0 of 0 stars") in screen readers.
