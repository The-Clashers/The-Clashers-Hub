## Decisions

- The icon map lives in `src/lib/`, not `src/engines/`. The map is data, not
  analysis logic; `lib/` is the home for pure helpers (STD-09). The rushed
  engine imports from `engines/`; the grid imports from `lib/` for the icon
  map and from `engines/` for the category reference lists (SIEGE_MACHINE_NAMES,
  PET_NAMES) so the two views agree on categorization.
- The icon imports use ES module imports (not stringified paths) so Vite
  treats them as first-class build assets: it hashes them, the bundle scan
  sees them, and a missing file fails the build instead of the render. The
  placeholder SVG is imported the same way.
- The grid keeps super troops. The rushed engine drops them (a super
  troop's level is the boosted variant's scale, not the real lab level),
  but the grid is an inventory view: the player can see which super troops
  are active. The two views disagree on inclusion by design, never on
  categorization.
- The grid shows both villages. The rushed analysis is home-village only
  (05 section 1); the grid shows both (FR-16 names "both villages"). The
  adapter does not filter by village; the village grouping is the render
  shape, not a filter.
- The flat `heroEquipment` array is read by the grid (FR-16 names "hero
  equipment where exposed"). The hero panel reads only the nested per-hero
  equipment; the grid reads the flat inventory too, so every piece the
  player owns renders. Both arrays carry the same names, so the icon map
  serves both.
- The tile renders a MAX chip when level >= maxLevel (the global maximum
  the API reports). The maxed-for-Town-Hall chip (the indicator that reads
  against the bundled TH cap table, not the global maximum) lands with
  T-M2-6; until then, the tile renders the global-maximum reading. The
  tile's shape is designed so that change is a new field, not a rewrite.
- The grid is virtualized (FlatList) because ~100 tiles is the normal
  case (07 section 3). The village and category headers are items in the
  same flat list, not sticky headers: a 100-tile list scrolls fine without
  docking, and the flat list keeps the implementation simple. The
  initialNumToRender is 24 (enough to fill a viewport) and maxToRenderPerBatch
  is 24 (enough to keep scrolling smooth without jank).
- The tile row is one line: icon, name, level pair, MAX chip. The name
  flexes so a long name (Electrofire Wizard) does not push the level off
  the row; the level pair is a fixed width so columns of tabular figures
  align without the chip guessing at content width.
- The BB Baby Dragon icon is not in the map because the name "Baby Dragon"
  collides with the home village's Baby Dragon (the map is keyed by name,
  and the API uses the same name for both villages). The home village icon
  is what the map carries; a BB Baby Dragon renders the placeholder, which
  is the honest fallback (07 section 7). Splitting by village would require
  the tile to carry the village into the lookup, which is a T-M2-6 concern
  (the reference data bundle owns the icon map's completeness).
